# 日记本（Diary）

让 QQ bot 拥有**叙事性长期记忆**：记得更久远的事，换一个新会话后记忆和说话风格仍然保持连续。

## 它和现有记忆功能的区别

项目里已经有三套记忆，日记本是第四套。它们的边界是刻意分开的：

| 模块 | 记的是什么 | 粒度 | 谁写入 | 解决什么 |
|---|---|---|---|---|
| `owner-memory.js` | 关于主人的**事实** | 一句话 | 后台提炼 | 记性准（谁是谁、喜欢什么） |
| `slang-learner.js` | 黑话、网络梗 | 一个词 | 学习任务 | 听得懂群里的说法 |
| `tieba-style` | 语感、口头禅 | 风格片段 | 采语料 | 说话的味道 |
| **`diary.js`** | **发生过什么的叙事** | **一段** | **AI / 手动** | **记性长、人格稳** |
| `diary-core.js` | **不该遗忘的事**（承诺/边界/关系/喜好） | 一条 | 从日记提炼 | 不忘事 |
| `diary-grade.js` | 上面两者的分级尺子 | — | 纯计算 | 防模型自评失效 |

一句话区分：**事实层回答「主人是谁」，日记层回答「我们一起经历过什么」，核层回答「我答应过他什么、我不做什么」。**

事实层是「无时间的人设档案」——「主人备考公安联考」。它答不了「上周三我们聊到凌晨那次是什么感受」。
长期陪伴要的不是档案，是共同经历。

## 三个能力对应你的三个要求

### 1. 记录日记
- AI 通过 `qq_diary_write` 工具主动写
- 后台定期把对话整理成日记（与事实提炼同构的三重闸门：量够 + 冷却到 + 开关开）
- 写入时**当场脱敏**：`password:`、`sk-xxx`、身份证、银行卡、长 base64 串会被替换成 `[已省略]`

### 2. 记起更久远的事
`qq_diary_recall` 按「关键词 + 标签 + 人物 + 心情 + 时间窗口 + 重要度」检索。

**`q` 可以整句说人话**，不必自己拆词。例如：

```
q=你还记得我上次说膝盖疼的事吗
q=我说想抱你是什么时候
q=我是不是总被说像AI
```

服务端会先做**查询理解**（`parseQuery`），再打分：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| 去噪 | 剥掉「你还记得 / 我上次 / 我之前是不是说过 / 什么时候 / 关于…的事」 | 不剥的话中文 bigram 会切出「你还」「还记」「我上」这些碎片，几乎每条日记都命中，真关键词被淹没 |
| 剥动词前缀 | 「说想抱」→「抱」，「说要装只手」→「装只手」 | 口语实词常被「说/想/要」包住，整段匹配会把「说想」当关键词，在无关日记上误撞 |
| 时间线索 | 「最近/这几天」→ 14 天，「前段时间/上周」→ 45 天 | **「上次/之前/以前」不当作时间线索** —— 那恰恰是在问更久远的事，收窄就把要查的挡在窗口外 |
| 同义扩展 | 语音↔RVC↔声音、考试↔联考↔备考、像AI↔人机… | 见「已知限制」，同义词表补的就是词面匹配的短板 |

打分是可解释的，没有任何学习参数：

```
score = (重要度 - 3) × 0.6
      + 时间衰减 × 1.2                     # 0.5 ^ (天数 / 半衰期30天)
      + 有更正 ? 0.3 : 0
      + log1p(字段加权命中) × 2.2 × (0.5 + 0.5 × 覆盖率)
      + log1p(同义词命中) × 0.45 × 2.2     # 弱于原词
```

字段权重：标题命中 ×3 > 标签/人物 ×2.5 > 正文 ×1。

**覆盖率**是整句提问能不能查准的关键：主词至少要有一半被这条日记覆盖才算命中
（`覆盖率 = 最长被包含子串长度 / 主词长度`）。没这道门槛，「说要装只手」会在
「他说要分给我吃」上撞到「说要」拿到满分，跟真正相关的那条同分。

**为什么不用向量数据库**：单机、Node 无外部依赖、日记量级在千条以内。
为了 1000 条日记引入 embedding 服务，是拿部署复杂度换几乎测不出的召回提升。
中文检索用「整句查询理解 + 整词 + 字二元组」混合，对真实问句已经够用，且完全可预测、可单测。

调研过 mem0 / m3-memory / remem-mcp / Graphiti(Zep) / mem0-hybrid-search 的做法，
可借鉴的三点是：**查询侧理解比后端复杂化收益大**、**CJK bigram 是中文检索的必需品**、
**同义/实体扩展要用表而不是模型**（小语料上更可控、可单测）。没有引入它们的依赖：
它们要么需要 Python/Neo4j/向量库，要么每次检索都要调一次模型 ——
对「QQ 消息到了要秒回」这个场景，多一次网络往返是不可接受的。

**顺带一个反直觉的点**：如果查询里有关键词，零命中的条目会被**丢弃**，哪怕它很重要、很新。
否则「查考试」会返回一堆因为「近期/重要」而排上来的无关日记。
但整句都是噪声时（「我最近怎么样」）不适用 —— 那时没有关键词，
退化为「近期 + 重要」的时间线浏览。

### 2.1 `weak` / `exact`：防模型顺杆编造

同义词表是有代价的：问「膝盖疼」时库里其实没有这条记录，
但同义表会把它连到「跑步/体测」，于是返回「六点二十跑操」。
模型看到这个很容易顺着答「记得，你说跑操膝盖疼」—— 那就是凭空编了一段经历。

所以检索结果区分两种：

- `weak: false` —— 命中了原词（标题或正文里有用户说的那个词）
- `weak: true` —— 只是同义词沾边

调用方还多给一个顶层 `exact`：`true` 表示至少有一条是原词命中，
`false` 表示这次**全是沾边**。此时 MCP 会在正文前面加一条硬提示：

> 注意：这些条目只是话题相近（同义词沾边），没有一条真正记着「膝盖疼」。
> 可以据此说"没记到具体这件事"，不要把它们当成你说的那条来复述。

对应测试：`只靠同义词沾边的结果标成 weak（防模型顺杆编造）`。
这条闸比召回率更值钱 —— 少记一件事只是遗憾，编一件没发生的事会直接毁掉信任。

### 3. 新会话保持记忆和风格
这是日记层最关键、也是事实层做不到的部分。

注入 prompt 时分三段，**不能合并**：

1. **【最近的日记】** —— 维持连续感（「昨天聊到的那个」）
2. **【相关的旧日记】** —— 按本轮用户消息检索，回答「更久远的事」
3. **【说话风格参考】** —— 取高重要度的**原话片段**（`quote` 字段）

第三段是「风格一致」的关键。新会话的模型没有旧会话的上下文，
它需要的是**样板语料**——自己过去怎么说话。这只能由日记里的原话提供，
事实层（第三人称叙述）给不了。

`quote` 字段因此在 `normalizeEntry` 里被原样保留，任何「整理」都会让锚点失效。

## 核层：不该遗忘的那一类

日记会慢慢变淡，但有些事不该变淡。核层（`diary-core.js`）把它们单独提出来，常驻注入、**不参与衰减**。

四类，来源是「从日记里提炼」：

| kind | 含义 | 例 |
|---|---|---|
| `promise` | 答应过但还没做完的事 | 答应给他发一条QQ空间说说 |
| `boundary` | 绝对不做的事 | 不叫他主人 |
| `relation` | 我们之间是什么关系 | 他把我当自己人 |
| `preference` | 他明确喜欢/讨厌什么 | 喜欢短句，讨厌长解释 |

### 为什么需要它（实盘数据）

原来的日记只有一条衰减曲线，`importance` 是模型自评的重要度。
85 条真实日记的分布是：

| 5★ | 4★ | 3★ | 2★ |
|---|---|---|---|
| 1 条 | 13 条 | **51 条（60%）** | 23 条 |

模型写日记时天然倾向选「一般」——那最安全。于是所有依赖 importance 的机制一起失效：
`capEntries` 的 pinned、`shouldFold` 的保护、`memoryScore` 的分层，全部退化成一条线。

**结论：模型自评重要度不可信。** 那一类结构上就不该衰减的东西，必须从日记层提出来，
单独放一层，压根不参与衰减。这样情景层就可以放心大胆地忘——重要的已经提走了。

### 核层怎么长出来

**纯规则，不额外调用模型。**

第一版写成「往日记整理那个学习会话再排一次 prompt，然后等 turn」。
上线后日志立刻出现：

```
15:33:11 [bridge] 核层巩固失败（不影响日记与对话）：等待学习会话 turn 超时(120000ms)
```

原因是日记整理本身的 turn 可能还没结束，第二条 prompt 排队后与第一个 waiter 的对应关系就乱了，
最多白等 2 分钟。日记整理是**每轮对话都可能跑的热路径**，不能在这里多挂一次 LLM 往返。

所以改成：日记整理写完这一批之后，直接用 `ruleTags` 过一遍新条目，
命中 `promise` / `boundary` 的（且通过核层准入）就进核层。
零额外调用、零额外延迟、可单测。

代价：提炼质量不如 LLM。缓解有两层——
模型随时可以用 `qq_diary_core(action=add)` 主动补一条，
`qq_diary_promise_close` 负责关闭。规则只是兜底，不是唯一入口。

### promise 有终态

与日记的「只增不改」不同，承诺必须有终态，否则模型会反复追问已经做完的事。
用 `qq_diary_promise_close` 标成 `done` / `dropped`，**只有未完成的才注入**。

不确定做没做时不要关——关掉等于主动忘掉欠着的事。

### 预算

- 常驻注入上限 600 字（含前缀），每类最多 6 条
- 单条正文上限 80 字
- 上限 120 条，超了先淘汰已结束的 promise，`boundary` 优先保留

核层是**每轮都要发给模型的固定成本**，所以准入很严：寒暄和一次性事件一律挡在门外。

## 分级：为什么不能靠模型自评

`diary-grade.js` 用两把尺子给「这条多重要」定级。

**第一把是标签**（可验证）：
> 模型说的「这很重要」无法验证，但「这句话里有『不许』」是可以验证的。

| 规则 | 效果 |
|---|---|
| `FLOOR = {identity:4, preference:4}` | 身份/偏好至少 4 级 |
| `CAP = {routine:2, transient:1}` | **寒暄封顶 2 级，一次性事件封顶 1 级** |
| `BOOST = {promise:+1, stress:+1, emotion:+1}` | 加成，但不能突破 CAP |
| `HARD = {boundary:5, milestone:5}` | 硬标签直接定档 |

`CAP` 是整套机制存在的理由：没有它，每天的「晚安」「吃了吗」会被写成一堆 3 星条目，
把注入名额占掉，真正重要的事被挤出去——正是原来的实盘症状。

顺序是刻意的：**基础档 → 硬标签定档 → BOOST 加成 → FLOOR/CAP 夹逼**。
夹逼放最后，才能保证「不管前面怎么加，寒暄都上不去」。

冲突时 CAP 优先于 FLOOR：少记一条不重要的事，比把不该忘的事压在寒暄堆里强。

**第二把是行为信号**（客观）：

| 信号 | 条件 | 理由 |
|---|---|---|
| 被反复想起 | `recallCount >= 3` | 次线性，第 10 次不该比第 2 次强 5 倍 |
| 被纠正过 | `corrections > 0` | 说明这条被反复确认 |
| 话题复现 | `recurrence >= 3` | **最有价值**：连着三周说膝盖疼，就不是一次性事件了 |

只靠标签会漏掉「同一件事反复出现」，只靠行为冷启动时又等于不分级。所以两者都要。

### 一条硬规则：否定词不同，不算重复

```js
const NEGATIONS = ['不','没','别','勿','未','无','甭','莫'];
```

「不叫他主人」和「叫他主人」在字符包含判断下会被判成同一条——
剥掉否定字之后含义完全反转，而且丢的是最不该丢的那条边界。
所以 `findDuplicate` 在判断包含关系**之前**先比否定签名。

## 隐私边界（最重要的一条）

**两本日记，按会话分开，互不可见。**

| 谁 | 落盘 | 注入 | 读写 |
|---|---|---|---|
| 主人（本人私聊） | `state/diary.jsonl` + `state/diary-core.jsonl` | 全部条目 | 可写、可查、可更正 |
| 其他白名单成员（各自私聊） | `state/diary-others.jsonl` + `state/diary-others-core.jsonl` | **只有他自己那几条** | 只能读写自己的 |
| 群聊 | 不落盘 | 不注入 | 一律 403 |

四道闸：

1. 工具层：`qq_diary_*` 检查 key 必须是 `private:<数字>`，群聊直接拒绝，不发请求
2. 服务端：`/api/socialV2/diary` 再查一次；主人走 owner 库，其他人走 others 库
3. 归属过滤：others 库是**所有人共用一份文件**，所以每条都带 `key`，
   读取/更正前按 `key` 过滤一次 —— 漏了这一步，文件虽然分开了，
   但 A 的日记会出现在 B 的会话里，是比文件混用更隐蔽的泄漏
4. 注入层：`diaryBlockFor` 主人只拿 owner 库、其他人只拿自己那几条

还有一道在**上游**，比上面四道都更容易漏（因为文件是对的，只是生成日记的那张"草稿纸"是同一张）：

5. **整理会话隔离**：主人日记走 `ownerLearnerSessionId`（与事实提炼共用），
   他人的日记走**独立的** `diaryOthersSessionId`（工作区 `state/diary-others-agent`，标题「他人日记整理」）。
   `api.sessions.prompt` 是往同一个 sessionId 排队、**上下文会累积**——
   共用一个会话时，主人刚聊的私事仍在历史里，下一个人整理日记时模型看得见，
   可能被写进 `diary-others.jsonl`。那一刻文件按 key 分开了，内容却已经串了人。

**为什么必须分层**：工具层能绕过，服务端才是真正的那道门；
注入层则防住「以后有人改了前两道但忘了这里」；
整理会话隔离则防住「前四道全对，但内容在生成阶段就混了」。

**为什么主人和其他人要物理分开**：主人的日记里有主人的生活、备考、身体状况。
写在同一本就意味着两件事同时发生 —— 别人可以往主人的记忆里塞内容（间接污染人格上下文），
主人的私事也会随「近期日记」注入到别人的会话里（等于当众朗读）。

群聊里任何人的日记都不能被念出来——这是本项目最不能犯的错误。

## 数据与一致性

`state/diary.jsonl`（主人）与 `state/diary-others.jsonl`（其他白名单成员），都是 append-only JSONL。

- 逐行独立解析，坏一行只丢一行（不像 JSON 数组会整库失败）
- 纠错走 `appendCorrection`：原文**永不被改写**，纠正挂在 `corrections` 里
- 更正时必须传整本（`appendDiaryCorrection` 会 writeAll 整个数组），
  只传子集会把别人的条目抹掉 —— 所以服务端用 `bookAll` 而不是 `bookMine`
- 上限 5000 条，裁剪时 5 星永不删除
- 加载失败时降级为**只读**，绝不拿内存空库覆盖磁盘

## 配置

`config.json` 的 `diary` 段：

```json
{
  "diary": {
    "enabled": true,
    "minMessages": 15,
    "batchMessages": 30,
    "writeCooldownMs": 3600000,
    "learnerPreset": "qq-chat",
    "workspaceTitle": "他人日记整理",
    "recentDays": 7,
    "injectRecent": 5,
    "injectRecall": 4,
    "injectStyle": 3,
    "fold": true,
    "core": true,
    "coreInjectMaxChars": 600
  }
}
```

`learnerPreset` / `workspaceTitle` 只影响**他人日记**那条独立会话
（主人日记与事实提炼共用 `ownerMemory.learnerPreset`）。
`injectStyle: 0` 可单独关掉风格注入（保留记忆但不注入原话）。
`fold: false` 完全退回折叠功能上线前的行为（所有条目按条数上限展开）。
`core: false` 关掉核层（不再提炼、不再注入），日记与衰减不受影响。

工具开关在 `socialV2.tools.diary`，与 `memory` **分开**：
主人可能想关掉这种带主观叙述的记忆，但不影响轻量记忆。

## HTTP API（控制台/调试）

```
GET  /api/socialV2/diary?key=private:<QQ>&q=联考&limit=20
GET  /api/socialV2/diary?key=private:<QQ>            # 不带 q = 最近 20 条
POST /api/socialV2/diary          { key, token, body, title, mood, tags, quote, importance }
POST /api/socialV2/diary/correct  { key, token, id, text }

GET  /api/socialV2/diary/core?key=private:<QQ>&kind=promise&status=open
POST /api/socialV2/diary/core     { key, token, action:'add', kind, text }
POST /api/socialV2/diary/core     { key, token, action:'close', id, status:'done' }
```

**没有删除端点**。这是刻意的：一旦允许模型改写/删除人物认知，
一次幻觉就会永久污染它对这个人的记忆。纠错只能追加。
核层同样没有删除：承诺只能「关闭」（`done`/`dropped`），保留「答应过」这个事实。

```bash
npm run test:diary
```

- `scripts/test-diary-e2e.mjs` —— 7 项端到端（持久化、跨会话风格、久远召回、注入体积、HTTP 隐私闸门）
- `scripts/test-diary-mcp.mjs` —— MCP 工具注册与描述约束

超长查询（60+ 字）约 45ms，仍远低于一次模型往返。

## 已知限制

1. **后台自动整理依赖学习会话可用**。DSH 未就绪时会跳过，不报错（日记是增值能力，不该阻塞聊天）。
2. **同义词表是手写的，覆盖面有限**。语音/考试/AI味/跑操/空间这些高频话题已经建组，
   冷门说法仍可能查不到。补法是往 `SYNONYM_GROUPS` 加组，不是引入向量库 ——
   表可以单测、可解释，模型调用不能。
3. **`weak` 只是提示，不是硬拦截**。模型仍可能忽略它去编。这层防线依赖工具描述里
   写清「weak 为 true 时不要当成你说的那条来复述」，以及顶层 `exact:false` 那段前置提示。
4. **注入预算**：`recentMax + recallMax + styleMax` 三段合计约 2-4KB，已由测试锁定上界。
   日记正文很长时按 220 字符截断。
5. **重复记录去重依赖正文高度重合**（Jaccard > 0.72）。改写幅度大的重复条目不会被抓到 ——
   这是刻意取舍：阈值放宽就会把「三次被说像AI」这种真实的多次经历也合并掉，
   而那正是用户想查的频次。
